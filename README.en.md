# VBIOS Studio

[简体中文](README.md) | **English**

> [!WARNING]
> ## ⚠️ Testing incomplete / Not validated on real hardware
>
> **This project has not been validated on a real GPU.** We have not applied edited images, written Windows registry overrides, injected the Linux loader, or performed any flash operation on real hardware. Automated tests cover only offline parsing, synthetic ROMs, fake registry/command runners, dry-run behavior, and xvfb offscreen UI.
>
> - Historical user reports from the upstream projects **do not mean this project has been validated**; results can differ completely across vendors, models, cooling designs, and power delivery.
> - Modifying a VBIOS can cause crashes, display corruption, overheating, permanent hardware damage, or loss of warranty.
> - **A modified image loses its signature; never flash it with nvflash.** Modified images can only be applied through the Windows registry override or the Linux loader.
> - The flash path accepts **pristine factory images only**, with every check required; this project disables flashing by default.
> - You assume all risk. See [`docs/risk-model.md`](docs/risk-model.md), [`docs/security.md`](docs/security.md), and [`docs/testing.md`](docs/testing.md).

VBIOS Studio is a GTK4 graphical NVIDIA VBIOS editing and application suite built on [Panchovix/nvidia-vbios-vix-editor](https://github.com/Panchovix/nvidia-vbios-vix-editor) and [nvidia-windows-vbios-vix-loader](https://github.com/Panchovix/nvidia-windows-vbios-vix-loader): open and inspect a ROM offline, edit fields presented under the T0–T3 risk model (including experimental fields), generate a new VBIOS and loader payload, and apply changes through a controlled loader override. Bilingual Chinese/English, for Windows and Linux.

> **Project status**: v0.1.0 has been released; v0.1.1 is a patch release. The GUI diff/profile views and production controller wiring (`build_gui_controller()` in `app/container.py`, `adapters/diff.py`, `adapters/profile.py`) are in the source tree and covered by `tests/integration/test_real_controller.py`; they have not been validated on a real GPU.

## Features

Maps to GUI-01–GUI-10 in [`docs/requirements.md`](docs/requirements.md) §4:

1. **Top toolbar**: open / save as / undo / redo / search / language / theme / help, all with shortcuts and tooltips.
2. **Left navigation + file information card**: product name, PCI ID, BIOS version, and the image-chain list (index / type / size / whether the 8-bit checksum is balanced).
3. **Table view ↔ form view**: the table has fixed columns for field, current value, unit, range, default, risk badge, and raw offset; sortable by column.
4. **Search and filtering**: three independent switches (modified only / experimental T3 only / current section only) plus a live match count.
5. **Undo / redo**: at least 20 steps, `Ctrl+Z` / `Ctrl+Y` / `Ctrl+Shift+Z`; opening a new ROM clears both stacks.
6. **Preset profiles**: save a set of changes as JSON and apply it to another ROM; architecture mismatches are rejected as a whole with zero partial writes.
7. **Dual-ROM diff view**: field level (equal / different / left-only / right-only) plus image level (index, type, size, checksum, difference count).
8. **Apply / flash panel**: device status card, dry-run preview, execute and restore; every write requires a second confirmation.
9. **Empty state and error experience**: drag-and-drop guidance, a unified copyable error dialog, a shortcut table in Help, and the test disclaimer in About.
10. **Accessibility**: all controls are Tab-reachable and have accessible labels; risk colors are consistently T0 gray / T1 blue / T2 orange / T3 red, and color is never the only information channel.

## Risk levels (T0–T3)

| Level | Meaning | Default UI | Gate |
| --- | --- | --- | --- |
| **T0** | Read-only / informational: parsing, display, validation, diff, language and theme | Visible | None; read-only fields cannot be edited |
| **T1** | Low risk: only reduces electrical/thermal envelope or adds cooling headroom; reversible by reboot | Visible | Normal confirmation |
| **T2** | Medium risk: power/clock/fan policy changes that may crash or cause thermal throttling | Visible (experimental fields carry a badge) | Confirmation + change preview before apply |
| **T3** | High risk / experimental: voltage, current/OCP, protection thresholds, advanced power behavior | **Hidden by default** | Unlock experimental mode + per-field second confirmation + overall apply confirmation |

For complete field ownership, direction rules, and evidence, see [`docs/risk-model.md`](docs/risk-model.md). Experimental does not mean “safe to change freely”: T3 fields are neither visible nor writable before unlocking.

## Safety boundaries (read first)

1. **A modified image loses its signature; nvflash flashing is forbidden.** Editing does not re-sign the image; nvflash will reject it or cause unrecoverable damage.
2. **The flash path accepts pristine factory images only**, and every check must pass: SHA-256 matches the original record, byte-for-byte equality, every image checksum is balanced, valid structure, PCI/subsystem ID match, supported nvflash version, administrator privileges, and explicit confirmation. Any failure rejects the operation before nvflash is started.
3. **The primary path is the loader override**:
   - Windows: write the driver registry values `vbios` / `EnableGpuFirmware` / `VixLoaderPreviousEnableGpuFirmware`, then restart the device with `pnputil /restart-device`; the flash chip is never written.
   - Linux: generate the payload and instructions for injection by `nvidia-linux-vbios-vix-loader` at boot; this project never elevates privileges automatically.
4. **Original files are read-only**: every save writes a new file plus a `.json` manifest; the original file's SHA-256 is verified throughout.
5. **Flashing is disabled by default**: even a factory image requires an explicit switch, `--i-understand-flash-risk`, and a second confirmation.

## Installation

**Windows 10/11 x86_64**

1. Download `vbios-studio-<ver>-windows-x86_64.exe` and `SHA256SUMS` from Releases.
2. Verify in PowerShell: `Get-FileHash .\vbios-studio-<ver>-windows-x86_64.exe`, then compare with `SHA256SUMS`.
3. Double-click to start. CI builds the exe with Nuitka onefile on `windows-latest`; it bundles the GTK4 runtime and makes no network request on first launch. Registry writes require administrator privileges.

**Linux x86_64 (glibc ≥ 2.39, GTK 4.14+)**

```bash
tar xf vbios-studio-<ver>-linux-x86_64.tar.gz
cd vbios-studio-<ver>
./bin/vbios-studio --version
xvfb-run -a ./bin/vbios-studio --selftest   # skip when no graphical environment is available
./bin/vbios-studio                          # CLI
./bin/vbios-studio-gui                      # GUI
```

System dependencies (Ubuntu/Debian): `sudo apt install python3-gi gir1.2-gtk-4.0 gir1.2-adw-1 libgtk-4-1`. The Linux package uses the distribution PyGObject; GTK is not bundled.

**Run from source** (Python ≥ 3.11):

```bash
python -m venv --system-site-packages .venv   # PyGObject comes from the system
. .venv/bin/activate
pip install -e .
python -m vbios_studio --version
python -m vbios_studio --selftest
```

## Quick start

1. Export the factory VBIOS from your own GPU (GPU-Z on Windows; `nvflash --save card.rom` on Linux, **read-only**).
2. Open VBIOS Studio: `vbios-studio --gui card.rom`, or launch it and drop a `.rom` file / press `Ctrl+O`.
3. Check the file information card and image chain: every image's 8-bit checksum should show balanced.
4. Select a section on the left and edit fields by T0–T3 badge; T3 fields require completing the risk confirmation under “Settings → Experimental features” first. Example: change a T2 power field and observe the “modified” marker.
5. Use `Save As…` (`Ctrl+Shift+S`) to generate a new ROM + `.json` manifest; the original file remains untouched.
6. Open the Apply panel, select the target GPU, run `dry-run` to preview the registry keys/byte count, then confirm execution; `Verify` compares byte-for-byte only when the platform provides an NvAPI running-image reader, otherwise it explicitly returns `VERIFY_UNAVAILABLE` (stored override is not treated as the running image); `Restore` returns to the previous state. On Linux the path only shows external loader guidance and `Verify` is explicitly unavailable.
7. If the driver rejects the override, the GPU runs the factory VBIOS; do not retry repeatedly—run `unload` first and check the driver version.

Command-line examples:

```bash
python -m vbios_studio --version
python -m vbios_studio --selftest
python -m vbios_studio --gui path/to/card.rom
```

## Testing and known limitations

**Most recent local full test run (2026-10-23)**: `pytest -q | tail -1` → **224 passed**; `ls tests/ui/test_*.py | wc -l` → **20**; `mypy --strict src/vbios_studio` → **77 source files**; `grep -c '^msgid' src/vbios_studio/i18n/locale/en/LC_MESSAGES/vbios_studio.po` → **282** (same for `zh_CN`). Static gates `ruff check`, `ruff format --check`, `lint-imports`, and `python -m vbios_studio --version` pass; see [`docs/testing.md`](docs/testing.md) for the test matrix and blind spots.

**Not tested / cannot be tested (must remain in release notes)**:

- ❌ Editing, applying overrides, stress testing, and long-term stability on real GPUs.
- ❌ Real Windows registry writes, driver restarts, and the full Verify flow; the Windows build is covered only by static CI configuration and the `windows-latest` job, not tested locally.
- ❌ Compatibility differences across vendors, models, cooling designs, and power delivery.
- ❌ Actual injection by the Linux loader (external project).
- ❌ Any flash operation (disabled by default; no real-hardware flash validation is performed).
- ❌ Whether future NVIDIA drivers will continue to support the override.
